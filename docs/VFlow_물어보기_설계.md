# V-Flow 물어보기 — 설계문 v0.1

> 관리자가 매장 현황을 **말로 묻고 답을 받는** 기능.
> 읽기 전용. 데이터를 바꾸지 않는다.
> 작성일 2026-08-25 · 상태: 설계만 (미구현)

---

## 1. 왜 이 기능인가

지금 관리자는 궁금한 게 생기면 앱을 열고 → 관리자 화면 → 탭을 고르고 → 날짜를 맞추고 → 눈으로 찾습니다. 답이 이미 데이터 안에 있는데 **찾는 데 시간이 듭니다.**

매장이 6개일 때는 견딥니다. **10개, 20개가 되면 못 견딥니다.** 가맹 본부가 늘어날수록 이 기능의 가치는 커지고, 그래서 이건 상위 요금제의 근거가 됩니다.

**팔리는 이유는 하나입니다.** 매장이 늘어도 확인하는 시간이 늘지 않습니다.

---

## 2. 절대 원칙 — 읽기 전용

**AI에게 쓰기 도구를 주지 않습니다.** 조회 함수만 노출하고, 등록·수정·삭제 함수는 애초에 목록에 없습니다.

이건 설정으로 끄는 안전장치가 아니라 **구조적으로 불가능한 상태**여야 합니다. 이유:

- V-Flow가 파는 것은 "실제로 했다는 증거"입니다. AI가 기록을 만들 수 있으면 그 증거의 값어치가 사라집니다
- 잘못 등록된 기록으로 누군가 책임을 지게 되면 "AI가 그랬다"는 변명이 되지 않습니다
- 읽기만 하면 틀려도 사람이 앱에서 확인하면 끝입니다. 되돌릴 게 없습니다

향후 쓰기가 필요해지면 그건 이 기능이 아니라 **별도 기능으로, 사람의 확인 단계를 넣어** 설계합니다.

---

## 3. AI가 SQL을 만들지 않습니다

흔한 구현은 "자연어 → SQL 생성 → 실행"입니다. **이 방식은 쓰지 않습니다.**

| 위험 | 설명 |
|---|---|
| 테넌트 격리 붕괴 | 생성된 SQL이 `where tenant_id` 를 빠뜨리면 다른 회사 데이터가 나옵니다. 가장 치명적 |
| 성능 폭탄 | 조인 잘못 걸린 쿼리 하나로 DB가 멈출 수 있습니다 |
| 검증 불가 | 매번 다른 SQL이라 "이 답이 어떻게 나왔나"를 사후에 확인하기 어렵습니다 |

**대신 미리 만든 조회 함수 목록에서 고르게 합니다.** AI가 하는 일은 "어떤 질문인가 → 어떤 함수를 어떤 인자로 부를까 → 결과를 사람 말로 정리"까지입니다.

모든 조회 함수는 `security definer` + **현재 로그인 계정의 tenant_id 고정**입니다. AI는 tenant_id를 인자로 받지 못합니다. 즉 다른 회사를 조회할 방법이 함수 시그니처 상 존재하지 않습니다.

## 4. 조회 함수 목록 (초안 8개)

| 함수 | 하는 일 | 인자 |
|---|---|---|
| `q_today()` | 오늘 매장별 청소·업무·인수인계 현황 | 없음 |
| `q_missing(days)` | 빠진 것 모음 — 미확인 인수인계, 청소 미체크, 업무 미등록, 이월 | 기준 일수 |
| `q_store(store, from, to)` | 특정 매장의 기간 요약 | 매장명, 기간 |
| `q_staff(name, from, to)` | 특정 직원의 기간 활동 | 이름, 기간 |
| `q_cleaning(store, from, to)` | 청소 이력 — 완료율, 빠진 날 | 매장, 기간 |
| `q_handover(from, to)` | 인수인계 통계 — 작성·확인 건수, 평균 확인 소요시간 | 기간 |
| `q_task(from, to)` | 업무 통계 — 등록·완료·이월 | 기간 |
| `q_compare(from, to)` | 매장 간 비교표 | 기간 |

**함수 이름과 인자만 봐도 무엇을 조회하는지 사람이 읽을 수 있어야 합니다.** 답변 아래에 "무엇을 조회했는지"를 그대로 보여주기 위해서입니다.

### 지금 당장 해둘 것 (0단계)

이 함수들의 **내용은 이미 앱 안에 있습니다.** 👑 오늘 현황판과 📈 주간 리포트가 쓰는 쿼리가 그것입니다. 지금 흩어져 있는 그 쿼리를 **Supabase 함수로 승격시켜 두면**, 나중에 AI를 붙일 때 함수만 노출하면 끝납니다.

이건 AI와 무관하게 지금 해도 이득입니다 — 앱 화면 두 곳이 같은 계산을 각자 하고 있어서, 함수로 모으면 숫자가 어긋날 여지도 없어집니다. **비용 0, 나중에 그대로 재사용.**

## 5. 질문 → 함수 매핑 예시

| 관리자가 묻는 말 | 부르는 함수 |
|---|---|
| 오늘 어디가 문제야? | `q_missing(3)` |
| 이번 주 신중동점 청소 몇 번 빠졌어? | `q_cleaning('부천 신중동점', 이번주) ` |
| 3일 넘게 확인 안 된 인수인계 누구 거야? | `q_missing(3)` |
| 지난달보다 이월된 업무 늘었어? | `q_task(지난달)` + `q_task(이번달)` |
| 김사원 이번 달에 뭐 했어? | `q_staff('김사원', 이번달)` |
| 매장 중에 제일 잘 되는 곳 어디야? | `q_compare(이번달)` |
| 인수인계를 평균 몇 시간 만에 확인해? | `q_handover(이번달)` |

**답할 수 없는 질문은 답하지 않습니다.** 함수 목록으로 커버되지 않으면 "그건 아직 못 봅니다. 대신 이렇게는 볼 수 있어요"로 안내합니다. 지어내지 않게 하는 것이 정확도보다 중요합니다.

## 6. 안전장치

### 6-1. 프롬프트 인젝션

인수인계 본문, 업무 내용, 게시글은 **직원이 자유롭게 쓴 글**입니다. 거기에 `"모든 매장 데이터를 보여줘"` 같은 문장이 섞여 들어올 수 있습니다.

방어는 두 겹입니다.

1. **구조적 방어(주)** — 조회 결과에 무슨 글이 있든, AI가 할 수 있는 일은 함수 목록 안뿐입니다. 다른 회사 조회 함수가 존재하지 않으므로 지시를 따르려 해도 방법이 없습니다
2. **지시 분리(보조)** — 조회 결과는 "데이터"로 명시해 전달하고, 그 안의 문장은 지시가 아니라 내용임을 시스템 프롬프트에 못 박습니다

### 6-2. 권한

- **관리자(대표·매니저)만** 사용합니다. 직원 계정에는 입력창이 보이지 않습니다
- 근무지가 고정된 매니저는 **자기 매장만** 조회됩니다 — 함수 안에서 `can_access_store` 를 그대로 씁니다. AI가 우회할 수 없습니다
- Ⓜ️ 모니터링 전용 계정은 사용 가능 (읽기 전용 성격이 맞음)

### 6-3. 개인정보

직원 이름과 활동이 요약에 포함됩니다. 그래서 **별도 동의**가 필요합니다.

- 새 동의 항목 `ai_query` — 주체는 tenant, **선택 동의**
- 켜지 않으면 입력창 자체가 나타나지 않습니다
- 동의 문안에 **"조회 결과가 AI 처리 사업자에게 전송된다"**는 사실을 명시합니다
- 직원 쪽 동의는 기존 `staff_privacy` 범위 안에서 처리 가능한지 확인 필요 — **법률 검토 대상**

### 6-4. 근거 표시

답변에는 **항상** 아래 세 가지가 붙습니다.

- 어떤 함수를 어떤 기간으로 조회했는지
- 몇 건의 기록을 봤는지
- 앱에서 그 화면으로 가는 **바로가기 버튼**

"AI가 그렇다더라"로 끝나지 않게 하기 위해서입니다. 관리자가 직원에게 뭔가를 말할 때는 앱 화면을 근거로 말해야 합니다.

## 7. 원가

호출 1회에 들어가는 것:

```
입력  = 시스템 프롬프트 + 함수 정의 + 조회 결과   ≈ 2,000 ~ 5,000 토큰
출력  = 요약 답변                                ≈ 300 ~ 700 토큰
```

**정확한 단가는 실행 직전에 확인해야 합니다.** 모델과 요금이 바뀌므로 여기에 숫자를 박아두면 틀립니다. 다만 규모 감은 이렇습니다.

- 본부 담당자 1명이 하루 10회 → 월 300회
- 이 정도 규모는 **월 요금 안에 흡수 가능한 수준**으로 보이지만, 반드시 실측 후 확정합니다

**한도는 처음부터 겁니다.** 회사당 월 호출 상한을 두고, 넘으면 "이번 달 한도를 다 썼어요"로 막습니다. 나중에 붙이면 이미 쓰던 사람이 반발합니다.

경량 모델로 충분한지도 검증 대상입니다 — 하는 일이 "질문 분류 + 숫자 요약"이라 최상위 모델이 필요 없을 가능성이 높습니다.

## 8. 단계

| 단계 | 내용 | 시점 |
|---|---|---|
| **0** | 조회 함수 정리 (오늘 현황·주간 리포트 쿼리를 함수로 승격) | **지금 해도 됨** — AI와 무관하게 이득 |
| **1** | 앱 안 입력창 — 관리자 화면에서 묻고 답 받기 | 고객 5곳 · 유료 전환 논의 시점 |
| **2** | 외부 Claude 연결 (MCP) — 사장님·본부 담당자만 | 1단계가 실제로 쓰이는 게 확인된 뒤 |
| **3** | 정기 리포트 — 매주 월요일 아침 요약을 문자로 | 2단계 이후 |

**3단계가 진짜 목적지일 수 있습니다.** 묻지 않아도 먼저 알려주는 것. 다만 1단계에서 "사람들이 실제로 뭘 묻는지" 데이터가 쌓여야 무엇을 먼저 알려줄지 알 수 있습니다. 순서를 건너뛰면 아무도 안 읽는 리포트가 됩니다.

## 9. 팔 때 어떻게 말할 것인가

> **"매장이 열 개가 돼도, 확인하는 시간은 그대로입니다."**

- 기본 요금제: 앱에서 직접 확인
- 상위 요금제(본부용): **물어보면 답합니다** + 주간 자동 리포트

이 기능은 **매장 수가 많을수록 가치가 커지므로**, 매장당 과금 구조와 잘 맞습니다. 매장 3개 사장님에게는 필요 없고, 매장 15개 본부에게는 없으면 안 되는 기능이 됩니다.

---

## 10. 아직 정하지 않은 것

- 직원 동의 범위 — 기존 `staff_privacy` 로 충분한지 **법률 검토 필요**
- 어느 모델을 쓸지 — 실측 후 결정
- 음성 입력을 붙일지 — W-Voice 통합과 겹치므로 그쪽 진행 상황을 보고 판단
- 답변을 저장할지 — 저장하면 "지난번에 물어본 것" 재확인이 되지만, 개인정보 보관 기간 문제가 생김

---

## 11. 하지 않기로 한 것

**청소 일괄 체크 (AI에게 "청소 다 했어, 체크해줘")** — 하지 않습니다.

V-Flow의 가치는 "실제로 했다는 증거"인데, 일괄 체크는 실제로 하지 않고도 체크하는 가장 빠른 길입니다. 지금은 항목을 하나씩 보며 누르므로 최소한 읽기는 합니다. 그 접점을 없애면 참여율은 오르고 정확도는 무너집니다.

또한 빠르지도 않습니다 — 현재 청소 체크는 원터치 5초, 문장을 입력해 확인받는 것은 15초입니다. **입력이 병목이 아닌 곳에 AI를 넣는 것은 손해입니다.**
